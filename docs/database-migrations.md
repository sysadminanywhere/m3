# Database migrations

PostgreSQL schema changes are managed by Liquibase 5, using the version supplied by Spring Boot 4. The control plane runs migrations before Hibernate starts and before it reconciles worker containers. Hibernate uses `ddl-auto=validate` in both the UI and worker applications.

## Automatic startup

Build with `./mvnw package` and run `java -jar m3-app/target/m3-community.jar` from the repository root, or start the stack with `docker compose up --build -d`. Liquibase uses the same datasource credentials as the application. There is no separate migration container or manually ordered SQL import.

The master changelog is `m3-core/src/main/resources/db/changelog/db.changelog-master.xml`. It records eighteen changesets:

1. Channels, channel properties, messages, message metadata and the legacy task table.
2. Rules, rule conditions and rule actions.
3. Worker pools, rule assignments and durable rule execution jobs; upgrades for older autoscaling and claim/result columns.
4. Worker pool CPU/RAM metric samples.
5. Indexes for worker claims, message history, rule lookup and metrics.
6. The `default` worker pool and assignments for existing rules without a pool.
7. The durable outbox for receipt notifications to external consumers.
8. Durable source delivery receipts for deduplication across retries and restarts.
9. Outgoing submission deduplication, retry scheduling, claim tokens and larger channel-name columns.
10. Original message bytes (`bytea`), charset and origin, compatible payload representation and legacy data backfill. See [message encoding and deployment](message-encodings.md).
11. Per-rule loading settings; moves existing polling, file-selection, deletion and Kafka consumer settings from source channels to their inbound rules. Channels without inbound rules remain idle.
12. Destination channel references, persisted receiver health and individual container metrics.
13. Recovery of orphan outgoing copies when their routing rule can be identified unambiguously.
14. HTTP ingestion request digests for idempotency conflict detection.
15. Metadata values stored as TEXT; duplicate keys retain the most recent value, then a unique message/key index prevents duplicates.
16. Payload media types extended to 255 characters.
17. Removal of configurable Kafka deserializers and activation of inbound endpoint records; rules control receivers.
18. Backfill the destination of inbound messages from their routed outgoing copies when the destination is unambiguous; manual forwarding does not change the source history.

Liquibase creates `databasechangelog` and `databasechangeloglock` in the current PostgreSQL schema. Its lock serializes concurrent control-plane startup. Existing changesets are checked by checksum and are not rerun.

The starter task feature has been removed from the application. Its table and sequence remain in the immutable baseline for compatibility with existing databases; M3 no longer reads or writes them.

Workers use `spring.liquibase.enabled=false` and only validate mappings. Start the control plane before launching standalone workers. Docker workers created by the UI receive `SPRING_LIQUIBASE_ENABLED=false` and `SPRING_JPA_HIBERNATE_DDL_AUTO=validate` explicitly. Rebuild the shared image when deploying new migrations so the UI and workers use the same schema version.

## Adopting an existing Hibernate database

The baseline uses `CREATE TABLE/SEQUENCE/INDEX IF NOT EXISTS`, so a compatible existing M3 database can be adopted without dropping tables, deleting records or resetting identity/sequence counters. The scripts add the worker-related columns missing from older M3 schemas and assign previously unassigned rules to `default`. An existing default pool retains its capacity and autoscaling settings. Foreign keys already generated by Hibernate are recognized by their relationship, even if their names differ.

Before the first deployment, take a database backup and stop the old UI and worker processes that still use Hibernate `ddl-auto=update`. Start the rebuilt control plane, let migrations and Hibernate validation complete, then launch rebuilt workers. Do not delete the Compose database volume to enable Liquibase.

Arbitrary incompatible schemas are not repaired automatically: Hibernate validation fails on missing mapped columns or incompatible types. Such changes require an explicit migration. The SQL does not replace existing constraints merely because their names differ from the baseline.

## Maven commands

The Liquibase Maven plugin uses environment variables rather than credentials stored in a configuration file. On PowerShell:

```powershell
$env:SPRING_DATASOURCE_URL = 'jdbc:postgresql://localhost:5432/m3'
$env:SPRING_DATASOURCE_USERNAME = 'postgres'
$env:SPRING_DATASOURCE_PASSWORD = '<database password>'
./mvnw.cmd -pl m3-core liquibase:validate
./mvnw.cmd -pl m3-core liquibase:status
./mvnw.cmd -pl m3-core liquibase:updateSQL
./mvnw.cmd -pl m3-core liquibase:update
```

On Linux/macOS, export the same variables and use `./mvnw`. Run `updateSQL` to inspect pending SQL before applying it. Routine startup already applies pending migrations; manual `update` is optional. The changelog's stable `logicalFilePath` makes Maven and Spring Boot share the same changeset identities.

To use a schema other than `public`, configure the connection URL consistently for migration and application processes, for example `jdbc:postgresql://localhost:5432/m3?currentSchema=m3`. The schema must already exist.

## Adding schema changes

Add a new numbered SQL file under `db/changelog/changes` and append a changeset to the master changelog. Keep applied changesets, IDs, authors and the logical file path unchanged. Include schema changes and any required data backfill in the same deployment as the corresponding entity changes. For PostgreSQL `DO` blocks, use `splitStatements="false"` on the `sqlFile`.

The baseline deliberately has no destructive rollback: it also adopts tables that may contain pre-existing production data. Recover with a tested backup or an explicit forward migration. Do not use `clearCheckSums` to hide edits to already applied scripts.

## Verification

```bash
./mvnw -Dtest=LiquibaseMigrationsTest test
```

These tests use a disposable PostgreSQL 17 Testcontainers instance and isolated schemas. They check fresh initialization, Hibernate compatibility, repeat startup, preservation of existing data and sequence counters, upgrades from before worker containers, and upgrades of older autoscaling/job schemas. Docker must be available; these integration tests are skipped when it is unavailable. They never use the application's configured datasource.

Integration details: [Spring Boot database initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html) and [Liquibase existing-project migration](https://www.liquibase.com/blog/adding-liquibase-on-an-existing-project).

# Обработка правил v2

Источник с `ruleSelection: ALL_MATCHING` создаёт отдельное задание для каждого подходящего включённого правила. `FIRST_MATCHING` создаёт одно задание для первого подходящего правила в порядке конфигурации.

Начальная загрузка YAML или JSON включается только явно: задайте `M3_BOOTSTRAP_ENABLED=true` и `M3_BOOTSTRAP_FILE` с путём к файлу, доступному приложению. Файл публикуется только в пустую установку; при наличии опубликованной версии он не применяется. При одновременном запуске реплик конкурирующая публикация не перезаписывает уже опубликованную версию. Ошибочная начальная конфигурация останавливает запуск.

В Docker Compose путь `M3_BOOTSTRAP_FILE` относится к файловой системе контейнера: файл необходимо дополнительно примонтировать только для чтения через локальный Compose overlay или иной механизм развёртывания.

В первом релизе условие правила — `condition.fileNameEquals`. При отсутствии условия правило подходит любому имени файла. Получатель-каталог получает неизменённые байты оригинала; доставка имеет семантику at-least-once, поэтому после сбоя или явного retry возможен дубликат.

Каталожный источник принимает файл только после стабильного наблюдения: размер и время изменения должны совпадать между двумя опросами с окном `m3.ingest.stability-window-ms` (по умолчанию 1000 мс). Первый опрос только запоминает состояние файла. Это снижает риск чтения файла, который ещё копируется во входной каталог; атомарное переименование файла источником всё равно рекомендуется.

Правило может указать `executionGroup` (по умолчанию `default`). Worker Community принимает только задания своей группы через `M3_EXECUTION_GROUP` или `m3.worker.group`; перенос группы влияет только на новые задания, уже созданные задания сохраняют исходную группу.

При проверке и публикации изменений Community предупреждает о переносе каждого существующего правила: указывает прежнюю и новую группу и напоминает, что ранее созданные задания остаются в своей группе. Для завершения старых заданий должны быть доступны исполнители прежней группы; неопределённые задания новой группе не передаются автоматически.

Явный retry использует версию существующего задания. Новая обработка оригинала (`reprocess`) заново выбирает правила по текущей опубликованной конфигурации и создаёт отдельные задания с текущими версиями и группами; это также позволяет обработать ранее не сопоставленное сообщение. При отсутствии источника или подходящих правил возвращается ошибка, а повторная доставка может создать дубликаты.

`processingMode: SEQUENTIAL` разрешает только одно выполняющееся задание правила в группе и выбирает задания в порядке создания. При `onError: STOP` (по умолчанию) ошибка или неопределённый исход блокирует последующие задания правила; `CONTINUE` позволяет продолжить. Ошибка до размещения итогового файла переводит задание в `RETRY` с автоматическим повтором и задержкой. По умолчанию неопределённый исход требует явной операции retry. `PARALLEL` остаётся режимом по умолчанию.

Во время доставки аренда продлевается каждые 15 секунд и проверяется перед публикацией файла. Потеря аренды не может отменить уже начавшуюся операцию файловой системы: её исход может потребовать решения оператора.

Задержка автоматического повтора растёт вдвое с каждой попыткой и ограничена сверху. `m3.delivery.retry-base-seconds` (по умолчанию 1) задаёт базу, `m3.delivery.retry-max-seconds` (по умолчанию 300) — предел; первая неуспешная попытка ждёт удвоенную базу, но не более предела. Для переменных окружения Spring используйте `M3_DELIVERY_RETRY_BASE_SECONDS` и `M3_DELIVERY_RETRY_MAX_SECONDS`; задавайте одинаковые значения всем репликам. Оба значения должны быть положительными, предел — не меньше базы.

Автоповтор неопределённого исхода может привести к повторной доставке. Он возможен только при одновременном явном `autoRetryUncertain: true` в опубликованной версии правила и `M3_DELIVERY_ALLOW_AUTO_RETRY_UNCERTAIN=true` на исполнителе нужной группы. Оба параметра по умолчанию выключены. После восстановления просроченной аренды история сохраняет `UNCERTAIN`, затем задание переводится в `RETRY` с обычной задержкой. Для единообразия задавайте настройку исполнителя одинаково всем репликам группы; уже созданные задания используют значение из своей версии правила.

Сервис периодически удаляет неиспользуемые content-объекты после семи суток с первого обнаружения отсутствия ссылок. Проверка ссылок и регистрация приёма синхронизированы через PostgreSQL; `m3.storage.orphan-retention-hours` может увеличить срок хранения, но не уменьшить его ниже семи суток. Копирование выполняется в `.m3-ingest-tmp` вне общей блокировки, а перед регистрацией проверяются аренда и актуальная версия конфигурации. Требуется атомарное перемещение внутри общего хранилища. Временные файлы, зарегистрированные в БД, очищаются после семи суток, если их владелец больше не имеет действующей аренды. Неучтённые файлы старых версий автоматически не удаляются.

Источник просматривает все обычные файлы в корне входного каталога, включая уже существовавшие до запуска и оставшиеся после простоя. Подкаталоги не обходятся. После запуска или смены владельца требуется новое стабильное наблюдение; приём возобновляется для файлов, которые всё ещё доступны. Сервис не удаляет и не перемещает входные файлы.

Дедупликация действует по паре идентификатора источника и SHA-256 содержимого сохранённого сообщения. Поэтому два файла с разными именами, но одинаковыми байтами, на одном источнике дают одно сообщение: условие по имени проверяется для первого принятого файла. Одинаковые байты на разных источниках учитываются отдельно. После удаления записи сообщения прежний файл, оставленный во входном каталоге, может быть принят снова. Такой механизм не гарантирует exactly-once для произвольного файлового источника; при необходимости различать события с одинаковым содержимым входной процесс должен обеспечивать различимые данные или отдельный протокол.

Перед размещением результата получателю Community сверяет SHA-256 временной копии с контрольной суммой оригинала в БД. При несовпадении итоговый файл не размещается, временная копия удаляется, а задание переходит в RETRY с причиной ошибки. Автоматические попытки продолжатся по расписанию: оператору следует восстановить оригинал из резервной копии и проверить integrity API.
